# Практическая работа: параллельная обработка данных с помощью Worker

Приложение считает статистику большого массива чисел (сумма, среднее, минимум, максимум) двумя способами: в основном потоке браузера и в отдельном Dedicated Worker. Время замеряется через `performance.now()`.

## Состав проекта

| Файл | Назначение |
|---|---|
| `index.html` | Страница: выбор размера массива, кнопки, счётчик, результат, журнал замеров |
| `main.js` | Основной поток: генерация массива, вычисление без Worker, работа с Worker, замеры |
| `worker.js` | Worker: вычисление по блокам, проверка отмены, ответ в формате `{ id, ok, result, error }` |
| `README.md` | Инструкция, описание реализации, таблица измерений и выводы |

## Инструкция запуска

Worker подключается как ES-модуль, поэтому страница **не работает при открытии файла двойным кликом** (`file://`). Нужен любой локальный HTTP-сервер.

1. Откройте терминал в папке проекта.
2. Запустите сервер (один из вариантов):
   - Python: `python -m http.server 8000`
   - Node.js: `npx serve .`
3. Откройте в браузере `http://localhost:8000` (или адрес, который покажет `serve`).

## Как пользоваться

1. Выберите размер массива и нажмите **«Сгенерировать массив»**.
2. Поле **«Нагрузка»** задаёт, сколько раз вычисление проходит по массиву. Простая сумма по миллиону чисел занимает миллисекунды, и зависание интерфейса не заметно. Повторы искусственно делают задачу длинной (и в основном потоке, и в Worker, одинаково). Подберите значение так, чтобы на 5 000 000 элементов основной поток считал 1–3 секунды.
3. Нажмите **«Считать в основном потоке»** или **«Считать в Worker»**. Во время вычисления смотрите на счётчик: если он остановился, интерфейс завис.
4. Результат и время записываются в «Журнал замеров». Оттуда переносите значения в таблицу ниже.
5. Дополнительные кнопки: **«Отменить задачу в Worker»**, **«Проверка ошибки»** (отправляет пустой массив), **«Завершить Worker»**.

## Как это работает

### Обмен сообщениями

Данные передаются через `postMessage` (массив копируется структурным клонированием).

Запрос в Worker:

```js
{ id: 1, type: "stats", payload: { array, repeats } }
{ type: "cancel", id: 1 }
```

Ответ из Worker:

```js
{ id: 1, ok: true,  result: { sum, average, min, max, computeMs } }
{ id: 1, ok: false, error: "текст ошибки" }
```

Идентификатор `id` позволяет сопоставить ответ с запросом. Ответы с неактуальным `id` игнорируются.

### Обработка ошибок

- В `worker.js` вычисление обёрнуто в `try/catch`. Ошибка (например, пустой массив) отправляется как `{ ok: false, error }`. Неизвестный тип сообщения тоже даёт `ok: false`.
- В `main.js` обработаны события `error` (Worker упал: показываем сообщение, закрываем его, при следующем запуске создаётся новый) и `messageerror` (не удалось прочитать сообщение).
- Для задачи в Worker стоит тайм-аут 60 секунд: если ответа нет, статус показывает ошибку, а Worker останавливается, чтобы запрос не висел вечно.

### Отмена задачи

Отмена кооперативная: Worker не убивается. Вычисление разбито на блоки по 100 000 элементов. Раз в 50 мс Worker на мгновение отдаёт управление (`setTimeout`), чтобы обработать входящее сообщение `{ type: "cancel", id }`, и проверяет, отменена ли текущая задача. Если да, отправляет `{ id, ok: false, error: "Задача отменена" }` и прекращает вычисление. Без этой паузы Worker не смог бы получить сообщение отмены, пока не закончит цикл.

### Завершение Worker

Worker создаётся при первом запуске и переиспользуется. Он останавливается через `worker.terminate()` в трёх случаях: по кнопке «Завершить Worker», при ошибке Worker и при тайм-ауте. `terminate()` принудительный: Worker не успевает завершить текущий шаг. Для отмены отдельной задачи используется протокол отмены, описанный выше.

### Замечания к измерениям

- Первый запуск Worker дольше остальных: в него входит создание самого Worker (в серии с нагрузкой 50 разница «всего» минус «внутри» составила около 18 мс против 1–6 мс на повторных запусках).
- Часть значений получена одним-тремя запусками, поэтому разброс между запусками заметен (например, Worker на 1 000 000 элементов: от 1199,7 до 1357,0 мс).

### Проверка корректности

Результаты (сумма, среднее, min, max) в основном потоке и в Worker для одного и того же массива совпали: `да`.

### Наблюдения за интерфейсом

- Основной поток, счётчик во время вычисления: останавливался на всё время расчёта (около 3,5 с на 5 000 000 элементов при нагрузке 600), интерфейс не реагировал.
- Worker, счётчик во время вычисления: продолжал обновляться, интерфейс оставался отзывчивым.
- Отмена задачи в Worker (5 000 000 элементов, нагрузка 600): после нажатия «Отменить задачу» статус показал «Задача N: Задача отменена», вычисление остановилось, интерфейс остался работоспособным.
- Проверка ошибки (пустой массив): статус «Задача N: Массив пустой», то есть Worker вернул `{ ok: false, error }`, а не завис и не упал.
- «Завершить Worker» и повторный запуск: после «Завершить Worker» статус «Worker завершён»; при следующем нажатии «Считать в Worker» создался новый Worker, и задача выполнилась как обычно.

## Выводы

1. Worker не ускорил вычисление, а замедлил его: при нагрузке 600 на 5 000 000 элементов основной поток считал 3488,3 мс, а Worker 6518,6 мс (примерно в 1,9 раза дольше), на 1 000 000 элементов 704,8 мс против 1293,0 мс, на 100 000 элементов 65,4 мс против 81,0 мс.
2. Ускорения не ждали: один Worker выполняет вычисление в одном потоке, как и основной поток, поэтому сама задача быстрее не становится, а ускорение возможно только при разбиении массива между несколькими Worker.
3. Размер замедления получился больше ожидаемого, и время вычисления выросло даже внутри Worker (6493,5 мс против 3488,3 мс); точная причина в работе не установлена, возможными факторами могут быть паузы для проверки отмены (`setTimeout`) и планирование потока браузером и системой.
4. Накладные расходы на передачу массива растут с его размером: разница между «всего» и «внутри Worker» составила около 1 мс для 100 000 элементов, 5–20 мс для 1 000 000 и около 25 мс для 5 000 000, потому что `postMessage` копирует массив структурным клонированием (`Float64Array` на 5 000 000 элементов занимает около 40 МБ).
5. При долгом вычислении эти расходы малы (около 0,4 % от общего времени на 5 000 000 элементов) и не объясняют разницу в несколько секунд.
6. На небольших данных Worker не даёт выигрыша: при нагрузке 50 на 100 000 элементов основной поток (9,2 мс) и Worker (8,6 мс) практически равны, а на 1 000 000 элементов первый запуск Worker занял 102,8 мс против 72,7 мс в основном потоке, потому что создание Worker и копирование массива сравнимы по времени с самим вычислением.
7. Главное преимущество Worker здесь в отзывчивости: при расчёте в основном потоке счётчик замирал на время вычисления, а при расчёте в Worker продолжал обновляться.
8. Таким образом, Worker оправдан для долгих вычислений, которые нельзя отдавать основному потоку из-за интерфейса, и не нужен для коротких задач.
9. Передачу массива можно удешевить через transfer list (`postMessage(msg, [array.buffer])`) или `SharedArrayBuffer`, но в этой работе это не проверялось.

## Краткое описание обработки ошибок, отмены задач и завершения Worker

- **Ошибки:** `try/catch` в Worker с ответом `{ ok: false, error }`; события `error` и `messageerror` в основном потоке; тайм-аут 60 с.
- **Отмена:** сообщение `{ type: "cancel", id }`; вычисление идёт блоками, и Worker раз в 50 мс отдаёт управление, получает сообщение отмены и проверяет, отменена ли задача; Worker при этом продолжает жить.
- **Завершение:** `worker.terminate()` по кнопке, при ошибке и при тайм-ауте; после этого при следующем запуске создаётся новый Worker.
